<objective>
Make Phase 1 business mutations replay-safe, make PATCH route IDs authoritative, define null/omission behavior, and prepare database-level tenant/payment invariants without connecting to or applying migrations against any database.

Purpose: Prevent a retry, mismatched route, or future data-write path from creating duplicate financial/stock effects or cross-organization relationships.
Output: API contract tests and implementation, a durable idempotency record in Prisma plus reviewed forward migration SQL, update DTO/controller/service contract fixes, and verification evidence. Migration application and DB integration remain an explicit user-authorization gate.
</objective>

</execution_context>

<decisions>
Use `Idempotency-Key` for state-changing operations in this plan. Recommend maximum 128 printable ASCII characters, minimum 16; scope the digest by organization, actor, HTTP method, and canonical route/operation. Persist SHA-256 key digest and canonical request hash, not raw key. Same scope/key/hash returns the original HTTP status/body; same key with different hash returns 409. Keep financial idempotency records without automatic expiry until a retention policy is approved. Because the record and business write share one transaction, concurrent identical requests serialize on the unique key; after the first commits the second replays. Record this contract in API docs/tests.

For PATCH, omitted means unchanged; explicit `null` clears only a nullable field; null on required fields is rejected. Route `:id` is authoritative. Preserve existing permission names and domain validation.

For schema work, add tenant-aware composite keys/FKs only where Prisma and PostgreSQL relations support them without unintended cascade changes. Add an exactly-one-payment-target database invariant only while Payment remains single-invoice-target; if Prisma cannot express the check, use a reviewed additive SQL migration constraint and document generated-client implications. Do not change accounting, costing, tax, refunds, payment allocation, or branch policies.
</decisions>
