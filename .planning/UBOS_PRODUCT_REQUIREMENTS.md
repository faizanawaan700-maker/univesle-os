# UBOS Product Requirements Map

**Scope:** requirements map for staged delivery. Items marked **Decision** must be settled before implementation; they are not assumed business rules.

## Roles and access baseline

Current evidence includes organization membership, roles, permission records, owner permissions, and server guards. There is no complete role/member administration UI, branch access workflow, or audit viewer. Preserve current permission keys and owner bootstrap during early changes. Any new roles or scopes require explicit migration and compatibility planning.

Target personas: Owner, Operations, Finance, Manager, Auditor. These labels do not prescribe permission grants. Define a permission matrix with the product/security owner before creating role-management features.

## Module requirements

| Module / purpose | Users and journeys | API / UI capability required | Data and rules | Permission / tests / dependencies | Acceptance criteria |
|---|---|---|---|---|---|
| Authentication & sessions — protect user access | User registers, logs in, views profile, logs out | Existing auth API/UI; later account recovery and session management | Users, password hashes, opaque session token hashes, expiry; never store raw tokens | Existing `AuthGuard`; unit tests plus API integration for expiry, origin, logout, throttling | Sessions expire/revoke predictably; secrets never appear in responses/logs; recovery cannot enumerate accounts |
| Organizations & membership — isolate business data | Owner creates/selects organization; later invites/removes member | Existing create/list/current; later invitation, acceptance, member and role management UI/API | Membership and role belong to same organization; invite state and expiry if approved | Preserve `organization.read/manage`; integration tests for cross-tenant and role changes | A user sees only authorized orgs; membership lifecycle is auditable and tested |
| Catalog — define sellable/buyable items | Owner/staff create categories/products, edit, archive, search | Existing category/product create/list and product update; UI edit/clear fields, barcode input, category management | SKU/barcode uniqueness per org; category and product same org; archive semantics | `catalog.read/manage`; DTO/service/API and browser tests | CRUD/archive/search works; referenced products remain historically identifiable |
| Inventory — know and change on-hand quantities | Staff receive, adjust, inspect stock movement, find low stock | Existing inventory list/adjustment and purchase/sale side effects; add paginated movement/detail views | Quantity cannot go negative unless a future policy explicitly permits it; every change links actor/reason/reference; warehouse dimension later | `inventory.read/manage`; transaction, concurrency, rollback and ledger reconciliation tests | On-hand equals opening + movements; failed operations leave no partial records |
| Customers & suppliers — manage counterparties | Staff add, inspect, search, edit contacts | Existing create/list/update API; UI update/clear fields, detail, archive policy | Org ownership; optional values distinguish omitted from clear; privacy/marketing consent policy | `customers.*`, `procurement.*`; DTO/API and browser tests | User can correct contact data without changing unrelated fields; access is org-scoped |
| Sales — issue customer invoices | Sales staff select customer/products, create multi-line sale, inspect detail | Existing create/list; add line editor, detail, search/paging, lifecycle corrections | Server-calculated Decimal totals; price snapshot; stock deduction and invoice creation atomic; status transitions require decision | `sales.*`, inventory interaction; integration, replay, concurrency, total reconciliation | Multi-line invoice totals match server; stock and invoice either both commit or both roll back |
| Procurement — receive supplier invoices | Staff select supplier/products, receive multi-line invoice, inspect detail | Existing create/list; add line editor, search/paging, receiving corrections | Unique supplier invoice number per org; receipt creates stock movements; cost policy **Decision** | `procurement.*` plus inventory permission as currently required; integration tests | One source invoice remains one record; stock and invoice reconcile; duplicate supplier invoice is safely rejected |
| Payments — record receipts and disbursements | Finance selects invoice, records partial/final payment, views history | Existing single-invoice payment/list; add idempotent create, reference field, allocation/adjustment workflow | Exactly one current target; no overpayment; multi-invoice allocation is a later accounting decision; immutable reversal preferred | `payments.manage`; unit, integration, replay/concurrency and reconciliation tests | Outstanding = invoice total − valid allocations; repeat request does not duplicate; every correction is traceable |
| Reports — summarize operating position | Owner/manager reviews sales, balances, inventory | Existing summary; add date filters, drill-down, export only after contract/security review | All values scoped and derived from consistent source records; inventory valuation method **Decision** | `reports.read`; reconciliation and pagination tests | Totals reconcile to their detail queries for the same scope/date range |
| Audit history — explain who did what | Owner/auditor filters activity and inspects an entity timeline | Events are written; add scoped read API/UI and export policy | Append-only event record, actor, action, entity, time, safe metadata and retention | Existing `audit.read`; authorization, privacy, retention and pagination tests | Authorized user can reconstruct changes; unauthorized tenant cannot read events |
| Accounting — produce financial books | Finance opens periods, posts/reconciles, closes periods | Not implemented; design before endpoints/screens | Chart of accounts, journal entries, balanced debits/credits, source references, period locks; accounting basis **Decision** | New explicit permissions; accounting design and reconciliation test harness | Every posting balances; subledgers reconcile; closed periods reject unapproved edits |
| Employees, branches & warehouses — delegate operations | Owner invites staff and assigns scoped access; staff work at location | Schema scaffolding exists; workflows absent | Member-org-role consistency; branch/warehouse dimensions on inventory and relevant events; assignments | RBAC compatibility plan; tenant/branch isolation tests | User can access only assigned scope; branch movement/report totals reconcile to org totals |
| Notifications, automation & integrations — connect systems | Admin configures external flows and alerts | Not implemented | Secret references, delivery state, retries, webhook idempotency, retention | Consent/security and provider decisions; contract and failure tests | Failed delivery is observable/retriable without repeating business effects |
| BI, AI, voice & document intelligence — assist decisions | Manager asks questions or reviews suggestions/documents | Future; no fake or placeholder automation | Explicit data access, provenance, confidence, approval state, model/provider boundary | Separate AI permissions; prompt/data-leak tests; human approval for high-impact actions | AI suggestions are attributable; financial/stock writes require explicit authorized confirmation |
| Localization & multi-currency — serve diverse markets | User selects locale/currency and sees localized values | Not implemented | Currency code and amount semantics; exchange-rate source/time; locale formatting; tax jurisdiction | Product/accounting decisions; currency conversion/reconciliation tests | Stored values preserve original currency and conversion provenance; formatting never changes stored amount |

## Cross-cutting business rules to ratify

1. Invoice tax: current inputs are fixed money amounts. Decide if percentage tax, tax codes, inclusive/exclusive tax, and jurisdiction rules are required.
2. Discounts: currently a fixed amount bounded by subtotal. Decide whether line-level discounts or percentage discounts are needed.
3. Costing: choose FIFO, moving weighted average, or another explicit policy before calling inventory value accounting-grade.
4. Corrections: define whether invoices can be voided before posting and how posted sales/purchases, stock, and payments are reversed.
5. Payment allocation: current schema attaches a payment to one invoice. Decide if one receipt can cover multiple invoices and whether overpayments become credits.
6. Branch/warehouse: decide if branch and warehouse are distinct, and which records carry each scope.
7. Deletion/retention: define archive, anonymization, legal retention, and immutable history rules before delete endpoints.

## Essential versus future

**Essential core:** idempotency, tenant integrity, multi-line invoices, invoice/contact detail and correction flows, pagination/search, audit visibility, stock reconciliation, and explicit costing/accounting boundaries.  
**Advanced/future:** AI manager, forecasting, voice, document extraction, multi-currency, external integrations, advanced CRM automation, and large-scale analytics. These depend on stable core data and permissions.
